### 一、架构哲学（The Philosophy）

Gio 的核心哲学可以浓缩成三句话：

1. **即时模式（Immediate Mode）是一等公民**  
   每一帧，程序都完整、显式地描述“当前 UI 应该长什么样”。框架不维护控件树，不隐式保存状态，不自动做 diff。

2. **描述与执行分离**  
   程序只负责生成**操作列表（op.Ops）**——一份纯数据的“绘制 + 输入注册”描述。真正的渲染、合成、事件路由全部交给驱动（Wayland / Win32 / Cocoa / Metal 等）去执行。

3. **零分配 + 确定性优先**  
   一切设计都围绕“能在每帧高频重建而不产生 GC 压力”展开。同时刻意用整数布局坐标系，保证跨平台布局结果完全一致、可测试。

这三点决定了 Gio 和其他主流 GUI 的根本差异：

| 维度       | Gio            | Flutter / React    | Qt / WinForms | Dear ImGui   |
| ---------- | -------------- | ------------------ | ------------- | ------------ |
| 模式       | 即时模式       | 声明式 + 虚拟树    | 保留模式      | 即时模式     |
| 状态归属   | 完全由程序管理 | 框架 + 程序        | 控件对象持有  | 程序管理     |
| 中间表示   | 操作列表       | 元素树 / Widget 树 | 原生句柄      | 直接调用绘制 |
| 性能关注点 | 零分配重建     | Diff + 保留层      | 原生性能      | 立即模式效率 |

Gio 更接近 Dear ImGui，但把“布局系统、输入路由、主题、单位”做成了完整、可组合的工业级方案，而不是只做游戏/工具向的简易 UI。

### 二、分层模型（Layered Architecture）

Gio 可以清晰地划分为 **5 层**：

```
┌─────────────────────────────────────────────────────────────┐
│  应用层（Application）                                      │
│  你的业务状态 + 自定义 Widget + Theme 选择                  │
└────────────────────────────┬────────────────────────────────┘
                             │ Layout(gtx)
┌────────────────────────────▼────────────────────────────────┐
│  组合层（Composition）                                      │
│  layout.Flex / List / Stack / Inset + material.* 控件       │
│  （约束计算、子控件编排、主题视觉）                         │
└────────────────────────────┬────────────────────────────────┘
                             │ 产生 op.Ops + event.Op
┌────────────────────────────▼────────────────────────────────┐
│  操作层（Operation）                                        │
│  op.Ops（绘制指令 + 输入注册 + 变换 + 裁剪 + 宏）           │
│  这是 Gio 的“中间表示 / IR”                                 │
└────────────────────────────┬────────────────────────────────┘
                             │ e.Frame(ops)
┌────────────────────────────▼────────────────────────────────┐
│  驱动层（Driver）                                           │
│  平台相关实现（渲染、窗口、输入设备、合成）                 │
└────────────────────────────┬────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────┐
│  操作系统 / GPU                                             │
└─────────────────────────────────────────────────────────────┘
```

**关键洞察**：

- **操作层是整个架构的枢纽**。上层所有 Widget、Layout、Theme 最终都只是在往 `op.Ops` 里写数据。
- 输入和绘制共享同一套 `clip` 区域树，这是 Gio 设计上的神来之笔，极大降低了概念数量。
- 主题（material）只是“组合层”的一种可替换实现，真正的核心在操作层和布局约束系统。

### 三、数据流与控制流（Data & Control Flow）

一个完整的帧是这样流动的：

```
1. window.Event() 阻塞等待
       ↓
2. 收到 FrameEvent
       ↓
3. ops.Reset()                     ← 清空上一帧操作
       ↓
4. gtx := app.NewContext(&ops, e)  ← 打包 Constraints + Ops + Source
       ↓
5. 你的 draw(gtx) / 根 Widget.Layout(gtx)
       │
       ├─ 处理输入事件（从 gtx.Source / gtx.Event 取）
       ├─ 根据业务状态 + 约束计算布局
       ├─ 调用子 Widget.Layout（递归）
       └─ 往 ops 写入 clip / transform / color / paint / event.Op
       ↓
6. e.Frame(gtx.Ops)                ← 提交操作列表
       ↓
7. 驱动执行：渲染 + 把新输入事件按 tag 分类存起来
       ↓
8. 回到 1，等待下一帧
```

**外部事件**（定时器、网络、文件变化）的介入方式只有一种：

```
外部线程修改状态 → window.Invalidate() → 强制产生下一帧 FrameEvent
```

这保证了**所有 UI 更新都发生在同一个单线程主循环里**，彻底避免了多线程 UI 的经典问题。

**输入的反向数据流**：

```
用户操作 → 驱动收集原始事件 → 按 clip 树 + tag 路由
       → 下一帧通过 Source.Event(Filter{Target: tag}) 返回给程序
```

程序必须在**当前帧**注册兴趣（`event.Op`），才能在**下一帧**收到对应事件。这是即时模式的经典延迟一帧特性。

### 四、关键设计取舍（Design Trade-offs）

Gio 做了很多“反直觉但深思熟虑”的选择：

| 取舍点       | Gio 的选择              | 放弃了什么                     | 获得了什么                         |
| ------------ | ----------------------- | ------------------------------ | ---------------------------------- |
| **模式**     | 即时模式                | 自动状态同步、细粒度更新       | 简单心智模型、易于推理、无隐藏 bug |
| **中间表示** | 操作列表（值类型）      | 面向对象控件树                 | 零分配、可录制回放、可缓存         |
| **布局坐标** | 整数像素                | 亚像素布局精度                 | 确定性、无半像素重叠、易测试       |
| **绘制坐标** | 浮点                    | —                              | 平滑动画、精确曲线                 |
| **颜色**     | sRGB 输入 + 线性混合    | 与部分老程序完全一致的混合结果 | 正确的半透明与抗锯齿               |
| **输入路由** | 基于 clip 树 + tag 冒泡 | 框架自动命中测试               | 与绘制完全统一、极度灵活           |
| **主题**     | 状态与视觉彻底分离      | 开箱即用的“完整控件”           | 可替换设计系统、高度可定制         |
| **单位**     | Dp / Sp 强制使用        | 直接写像素的简单性             | 真正的跨设备一致性                 |
| **动画**     | 显式 InvalidateCmd      | 框架自动帮你跑动画循环         | 完全可控、无后台偷偷重绘           |

这些取舍的共同点是：**把复杂性和控制权交给程序员，把性能和确定性留给框架**。

### 五、工程启示（Engineering Insights）

从 Gio 的架构中，我们可以提炼出对现代 GUI / 实时系统设计的通用启示：

1. **即时模式并非只能做简易工具**  
   只要把“布局约束 + 操作列表 + 输入注册”做成完整系统，即时模式完全可以支撑正式桌面/移动应用。

2. **中间表示（IR）是解耦的利器**  
   操作列表让上层 UI 代码与底层渲染/平台完全解耦，同时天然支持录制、回放、缓存、多线程准备（未来扩展）等高级能力。

3. **共享抽象能大幅降低概念负担**  
   用同一套 `clip` 同时服务绘制和输入，是典型的“一个好抽象消灭两个子系统”的例子。

4. **确定性比绝对灵活更重要**  
   整数布局坐标看似限制，实际上换来了可测试性、跨平台一致性和更少的视觉 bug。这在大型项目中价值极高。

5. **状态归属必须清晰**  
   Gio 强制你自己管理所有状态，反而避免了“框架状态与业务状态打架”的经典问题。配合“状态与视觉分离”，主题切换、自定义控件都变得简单。

6. **零分配是可以系统性追求的目标**  
   通过值类型操作 + `Add` 方法避免接口装箱、预分配 Ops 缓冲、Macro 复用等，Gio 证明了即时模式 UI 也可以做到接近零 GC 压力。

7. **单线程主循环 + 显式 Invalidate 是简单性的源泉**  
   所有 UI 更新都发生在同一个地方，推理成本极低。这比“任何线程都能改 UI”的模型更容易维护。

8. **分层要服务于可替换性**  
   material 包只是官方提供的一种视觉实现。真正的核心（op、layout、unit、text、color）保持中立，让社区可以做出完全不同的设计系统。

---

### 最终总结：Gio 到底是什么？

Gio 不是“又一个 Material Design 实现”，也不是“Go 版的 Flutter”。

它是一次**对即时模式 GUI 的系统性工程化**：

- 用操作列表作为统一 IR
- 用约束布局解决组合问题
- 用 clip 树统一绘制与输入
- 用明确的单位与颜色空间保证正确性与一致性
- 用零分配设计保证性能
- 用状态-视觉分离保证可定制性

它把“简单的心智模型”和“工业级的完整性”结合在了一起，代价是你需要比使用保留模式框架时多理解一些底层概念（操作栈、约束、tag、Invalidate）。

一旦跨越这条学习曲线，你会获得一个**极其透明、可控、高性能、跨平台一致**的 UI 基础。

这就是 Gio Architecture 在更高维度上真正想传达的东西。
