# A02

**找到了。** 你模糊记得的“省电”设计，正是 Gio 最核心、也最被低估的特性之一。

### 官方原文关键句（Drawing 章节）

> **Gio only issues FrameEvents when the window is resized or the user interacts with the window.**  
> However, animation requires continuous redrawing until the animation is completed. For that there is `op.InvalidateCmd`.

翻译并解读：

> **Gio 只会在「窗口大小改变」或「用户与窗口交互」时才发出 FrameEvent。**  
> 动画需要持续重绘直到完成，因此才提供了 `op.InvalidateCmd`。

这就是你记得的「省电」设计。

---

### 深度解读：Gio 的「按需重绘」省电哲学

大多数 GUI 框架（尤其是游戏引擎风格或很多现代声明式 UI）会：

- 以固定刷新率（60/120 FPS）持续跑主循环
- 即使界面完全静止，也在后台不断重绘
- 导致 CPU/GPU 持续占用，笔记本电池消耗明显

**Gio 完全相反**：

1. **默认完全静止**  
   当没有任何用户输入、窗口大小没变、也没有程序主动请求时，主循环会阻塞在 `window.Event()` 上，**几乎零 CPU 占用**。操作系统可以把进程挂起，非常省电。

2. **只在真正需要时才唤醒**  
   触发 FrameEvent 的情况主要有：
   - 用户鼠标/触摸/键盘操作
   - 窗口被调整大小、移动、显示/隐藏
   - 程序主动调用 `window.Invalidate()` 或在绘制时执行 `op.InvalidateCmd{}`

3. **动画是「显式申请」的**  
   需要动画时，你必须主动告诉框架「我还在动，请继续给我帧」：
   ```go
   if progress < 1 {
       source.Execute(op.InvalidateCmd{})  // 申请下一帧
   }
   ```
   动画结束后就不再申请，系统立刻回到「完全静止」状态。

这与传统「一直跑 60 帧」的即时模式（如早期 Dear ImGui 示例）形成鲜明对比。Gio 把即时模式的「每帧完整描述」和「事件驱动的休眠」结合在了一起。

### 实际效果与工程意义

| 场景                           | 传统持续刷新框架 | Gio              |
| ------------------------------ | ---------------- | ---------------- |
| 界面静止（用户在看文档、填表） | 持续 5~20% CPU   | 接近 0%          |
| 简单交互动画                   | 一直高占用       | 只在动画期间占用 |
| 笔记本电池                     | 明显消耗         | 非常友好         |
| 后台窗口                       | 仍可能重绘       | 通常完全休眠     |

这也是为什么 Gio 官方和社区经常强调它「高效」「适合桌面工具」的原因之一——它从架构层面就避免了无意义的重绘。

---

### 相关 API 回顾

- **`op.InvalidateCmd{}`**  
  在**当前帧的绘制代码里**执行，告诉框架「请尽快再给我一帧」。适合动画、进度条等。

- **`window.Invalidate()`**  
  从**任何 goroutine** 调用，强制唤醒主循环产生下一帧。适合外部事件（网络数据到达、定时器、文件变化等）。

两者配合，既保证了「需要时流畅」，又保证了「不需要时彻底休眠」。

---

### 总结

你记得的「独特省电设计」就是：

> **Gio 默认不刷新。只有用户交互、窗口变化，或程序显式申请（Invalidate）时，才产生 FrameEvent 并重绘。**

这是即时模式 GUI 里非常少见的「事件驱动 + 按需唤醒」组合，既保留了即时模式的简单心智模型，又获得了接近传统保留模式框架的省电特性。

这确实是 Gio 架构里一个很漂亮、也很务实的设计决策。
